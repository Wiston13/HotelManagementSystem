# HotelManagementSystem

**中小型連鎖商旅訂房與住宿管理系統**

## 專案簡介

HotelManagementSystem 是一套供中小型連鎖商旅使用的訂房與住宿管理系統。

系統整合顧客訂房、可售房量計算、分館住宿作業與後台資料管理，讓顧客、分館員工與總系統管理員共用一致的資料基礎，串接從線上訂房、入住、退房到清潔交接的完整住宿流程。

目前核心訂房與住宿管理流程已完成主要整合，專案仍持續進行功能擴充、跨模組整合、流程驗證與操作體驗調整。

## 系統設計目的

本專案不只提供個別資料的新增、查詢與修改，而是希望將商旅日常營運中彼此相關的訂單、住房紀錄、房型與房間整合成完整資料流：

**訂房 → 可售房量 → Check-in → 指派房號 → Check-out → 清潔**

系統透過各資料之間的關聯維持住宿流程的一致性：

- 顧客訂房時選擇房型，不直接指定房號。
- 已成立的訂單會依住宿日期占用對應房型的可售房量。
- 顧客抵達後，由分館員工於 Check-in 時指派符合條件的房間。
- Check-in 成功後建立住房紀錄，保存實際入住的房號與入住資訊。
- Check-out 完成訂單並將房間轉為待清潔。
- 清潔完成後，房間才可再次指派給下一位入住顧客。
- 清潔狀態影響入住時能否指派該房間，但不直接扣減未來住宿日期的可售房量。

## 使用者角色

### 顧客

顧客不需建立帳號即可使用訂房相關功能：

- 查詢分館與可售房型。
- 依住宿日期與入住人數篩選符合條件的房型。
- 選擇房型並填寫訂房資料。
- 完成信用卡付款流程模擬。
- 使用訂單編號與聯絡電話查詢訂單資訊。

### 分館員工

分館員工登入後，負責所屬分館的日常住宿營運作業：

- 查看分館員工首頁資訊。
- 查詢分館訂單。
- 處理訂單取消。
- 辦理 Check-in。
- 指派符合原訂房型的房間。
- 辦理 Check-out。
- 管理房間供應狀態。
- 處理房間清潔交接。

### 總系統管理員

總系統管理員負責跨分館的基礎資料與管理功能：

- 分館資料管理。
- 房型與固定價格管理。
- 房間資料管理。
- 分館員工帳號管理。
- 訂單 CSV 匯出。
- 系統重要操作紀錄查詢。

## 核心業務流程

目前系統主要住宿營運流程如下：

1. 總系統管理員建立分館、房型、固定價格、房間與分館員工等基礎資料。
2. 顧客依分館、住宿日期與入住人數查詢可售房型。
3. 系統依可供應房間數量、有效訂單與住房狀況計算各房型可售房量。
4. 顧客選擇房型並填寫訂房與付款資料。
5. 系統執行信用卡付款流程模擬。此專案不串接第三方金流，也不會產生真實信用卡扣款。
6. 付款資料驗證成功後，系統建立已付款訂單，並占用對應住宿日期的房量。
7. 顧客抵達分館後，由分館員工查詢並核對訂單。
8. Check-in 時，由分館員工從原訂房型中選擇符合入住條件的房間並指派房號。
9. Check-in 成功後建立住房紀錄，保存實際入住資訊。
10. 分館員工辦理 Check-out，完成訂單與住房流程。
11. Check-out 後房間轉為待清潔。
12. 清潔完成後，分館員工更新房間清潔狀態，使該房間可再次安排入住。

## 付款流程說明

本專案保留完整的付款操作流程，但不串接第三方金流服務。

顧客在訂房時仍需輸入信用卡相關資料，系統會進行必要的格式與資料驗證，並模擬付款成功或失敗的流程。

**此流程不會向任何信用卡或銀行發出實際扣款請求，也不會產生真實金流交易。**

付款流程驗證成功後，系統才會：

- 建立訂單。
- 將訂單狀態設為已付款。
- 占用對應住宿日期的可售房量。
- 顯示訂房成功結果。

如果付款流程失敗，則不建立正式訂單。

## 系統資料與業務規則

### 訂房與房號

顧客訂房時選擇的是「房型」，而不是特定房號。

例如顧客預訂的是雙人房，系統只會先保留一間雙人房的住宿需求，不會在訂房當下直接決定入住 301 房或 302 房。

直到顧客實際抵達並辦理 Check-in 時，才由分館員工依原訂房型以及當下房間狀態指派實際房號。

這讓「顧客的訂房需求」與「飯店實際安排房間」可以分開管理。

### 可售房量

系統依住宿日期計算各房型目前仍可接受多少筆訂房。

計算時主要考量：

- 目前可供應的房間數量。
- 已成立且會占用房量的訂單。
- 已入住且仍持續占用房間的住宿狀況。
- 房間保留、停用等供應狀態異動。

當員工或管理員準備保留、停用房間，或調整房間所屬房型時，系統也會檢查是否可能造成未來住宿日期的房量不足。

### 清潔狀態

清潔狀態主要用於判斷 Check-in 時哪些房間目前可以安排給顧客。

房間處於待清潔狀態時，不應被安排給新的入住顧客。

但清潔狀態不會直接扣除未來住宿日期的可售房量，因為該房間仍可能在未來入住日期前完成清潔。

### No-Show

系統會依目前時間、訂單住宿日期、訂單狀態及是否已有住房紀錄，判斷符合條件的逾期未入住訂單並更新為 No-Show。

### 操作紀錄

內部重要資料異動會建立操作紀錄，供總系統管理員查詢。

操作紀錄會顯示管理人員可直接辨識的資訊，例如：

- 分館名稱。
- 房型名稱。
- 房號。
- 訂單編號。
- 員工編號。

避免只顯示資料庫內部流水編號，讓管理人員能直接理解實際被操作的資料。

## 技術棧

- **程式語言：** C#
- **執行平台：** .NET 10
- **Web 框架：** ASP.NET Core MVC
- **資料存取：** Entity Framework Core
- **資料庫：** Microsoft SQL Server
- **前端：** Razor Views、Bootstrap、JavaScript、jQuery
- **版本控制與協作：** Git、GitHub

## 專案結構

- `Controllers/`：接收使用者操作、處理請求並協調 MVC 流程。
- `Services/`：放置跨功能共用或具有明確業務責任的服務邏輯。
- `Helper/`：電話正規化、狀態顯示等小型共用工具。
- `Models/`：資料庫實體、Entity Framework Core Context 與 ViewModel。
- `Views/`：顧客、分館員工與總系統管理員使用的 Razor Views。
- `database/`：資料庫 Schema、基準資料、開發情境與驗證腳本。
- `wwwroot/`：CSS、JavaScript、圖片及前端靜態資源。

## Git 協作流程

專案以 `develop` 作為團隊主要功能整合分支，成員透過功能分支與 Pull Request 進行協作：

**develop → feature branch → Pull Request → review → merge into develop**

各項功能在獨立分支進行開發與測試，完成後透過 Pull Request 進行程式碼審查，再合併回 `develop`。

開發期間亦會依功能責任拆分分支，並在合併前同步 `develop` 的最新變更，以降低整合衝突並維持主線穩定。
